# JRec 设计方案

这份文档记录的是**为什么这么做**，README 讲的是**怎么用**。

## 1. 目标与非目标

**目标**：一个自己能日常用的屏幕录制工具，Java 实现，代码结构经得起别人阅读，技术决策讲得出理由。

**非目标**（明确不做，避免范围失控）：

- 不做视频剪辑、拼接、加字幕 —— 那是另一个产品。
- 不做直播推流。
- 不做 iOS 端 —— Java 在 iOS 上没有运行时，这个题目本身不成立。
- 不追求超越 OBS。OBS 是场景合成软件，本项目是单文件录制工具，定位不同。

## 2. 用户与场景

一类人：需要向别人演示屏幕操作，但不想为了录一段 30 秒的演示去装一套 OBS。

典型场景：给同事录一个复现步骤、给自己留一份操作记录、录一段课程作业的演示。

由此推出两条硬约束：**启动要快**、**产物要是任何播放器都能打开的标准 MP4**。

## 4. 技术选型与取舍

### 4.1 采集与编码：调 FFmpeg 进程，不用 JavaCV

| 方案 | 判断 |
|---|---|
| `java.awt.Robot` 逐帧抓屏 + JCodec | 实测 1080p 下 10~15 帧，抓不到系统声音，音视频同步要自己写。**否** |
| JavaCV（Bytedeco） | 能用，但依赖 200MB+ 原生库，封装的仍是命令行。**否** |
| `ProcessBuilder` 调 FFmpeg | 参数完全可控，stderr 可逐行解析，核心零第三方依赖，仓库不带二进制。**采用** |

代价：用户机器上需要一个 FFmpeg 二进制。用「首次启动自动下载到 `~/.jrec/bin`」解决，而不是塞进仓库（GitHub 单文件 100MB 限制，且每次更新都要重新提交大文件）。

### 4.2 停止录制：发 `q` 到 stdin，不 kill

MP4 的索引（`moov`）在文件尾部，进程被强杀就写不进去，产物打不开。FFmpeg 支持 stdin 上的 `q` 正常收尾。所以停止路径是：写 `q` → 等 15 秒 → 不退出才 `destroy()`。

这条行为不是猜的，是先写了一个最小 Java 程序验证过 exit code 与产物完整性，才写进 `Recorder`。

### 4.3 区域录制：采集端裁剪，不录全屏再裁

`gdigrab` 的 `-offset_x/-offset_y/-video_size` 让抓屏器只读一块矩形，编码器从头到尾只看到用户选的那块。相比之下「录全屏再裁剪」要多解码一次全屏，纯属浪费。

macOS 的 `avfoundation` 没有这个能力，只能退回 `crop` 滤镜——代码里 `MacBackend.videoFilter` 与 `WindowsBackend` 的差异就是这件事的直接体现。

### 4.4 平台差异的收口：`CaptureBackend` 接口

Windows / Linux / macOS 的输入格式、设备寻址方式、裁剪能力全都不一样。全部差异压进三个 `CaptureBackend` 实现，`CommandBuilder` 和 `Recorder` 一行平台判断都没有。加一个平台 = 加一个实现类。

## 5. 踩到的坑与结论

**dshow 设备名不能加引号。** 设备叫 `麦克风 (ToDesk Virtual Audio)` 时，写成 `-i audio="麦克风 (...)"` 会直接 `I/O error`。原因是 `ProcessBuilder` 把每个参数作为独立 argv 交给 `CreateProcess`，没有 shell 参与，引号成了设备名的一部分。正确写法是 `-i audio=麦克风 (...)`。

`CommandBuilderTest.deviceNameIsNotWrappedInQuotes` 就是这条的回归防护。

**系统声音在 Windows 是权限与驱动问题，不是代码问题。** Windows 默认不开放系统播放声音的录制通道，必须有「立体声混音」或虚拟声卡。软件能做的是：检测不到时不假装能录，而是给出可操作的启用步骤（`WindowsBackend.systemAudioHint`）。

**HiDPI 下逻辑像素 ≠ 物理像素。** FFmpeg 的采集后端全在设备像素上工作，JavaFX 报的是逻辑像素。`RegionSelector` 用光标所在屏幕的 `getOutputScaleX()` 换算。混合 DPI 多屏下这个换算不成立，已列为已知限制。

**VBox 里的子控件不会自动撑满。** 历史区一开始下方一片空白，原因是 VBox 子节点 `maxHeight` 默认等于首选高度。要吃到剩余空间，必须显式 `setMaxHeight(MAX_VALUE)` + `VBox.setVgrow`。表格行的下拉框被挤出卡片也是同类问题，改用百分比列宽的 `GridPane` 才稳。

## 6. 测试策略

- **纯函数单测**：`CommandBuilder` 输出的参数数组、`FfmpegProgress` 的解析。不碰进程，毫秒级。
- **实拍测试**：真的起 FFmpeg 录 2 秒，用 `MediaProbe` 断言产物的分辨率与时长。没有 FFmpeg 的机器上 `assumeTrue` 自动跳过，不污染 CI。
- **UI 接线测试**：`UiFlowProbe` 通过反射驱动真实界面走完一次录制，验证监听器、视图切换、计时器、历史刷新这些单测够不着的地方。

三层覆盖的是不同东西：参数对不对、FFmpeg 认不认、界面连没连上。

## 7. 未解决的问题

1. **暂停/继续**：FFmpeg 无原生暂停。可行方案是分段录制 + `concat` 无损拼接，要处理段间时间戳对齐。
2. **崩溃安全**：先写 MKV（EBML 头在文件头，截断仍可播），停止时 `-c copy` 转 MP4。OBS 就是这么做的。
3. **长录制的 `+faststart` 开销**：`+faststart` 要在结束时重写文件，一小时录制会有几秒卡顿。可以和崩溃安全方案一起解决。
4. **Android 端**：`MediaProjection` + `MediaRecorder` 约 300 行。系统不支持原生区域录制，只能整屏，裁剪需后处理（且 Android 侧 FFmpeg 封装库 ffmpeg-kit 已于 2025 年初停止维护，属高风险依赖）。
